# #136 — исходный запрос → извлечение → обязательный оператор → ответ

2026-10-11. **Экспериментальный вход реализован и проверен; преимущество не подтверждено. Отрицательный результат применимости E2 сохранён. #136 OPEN.**

## Что реализовано

`raw_entry.py` принимает исходный текст из UTF-8 файла. Один вызов `raw_actor.py` через Codex app-server извлекает условия и одновременно готовит обычный ответ. Host проверяет форму, значения, точное вхождение цитат, явные UNKNOWN и различие direct/derived/unknown. Затем **безусловно запускает существующий `information_action.py` как subprocess**. Вызов происходит и при `correction`, и при ошибке извлечения; во втором случае CLI получает невалидный контракт и возвращает явную ошибку. Успешное action оператора становится пользовательским ответом; если action отсутствует, остаётся исходный draft; при невалидном контракте возвращается барьер.

Один вызов модели на вход; второй вызов для перефразирования не нужен. Модель не видит код оператора, готовый контракт, ожидаемые значения, правильный вопрос, рубрику или название случая. Она получает только исходный текст, общий prompt и структурную схему существующих полей. Схема задаёт измеряемые смысловые оси, поэтому это **не проверка свободного поиска без направляющей схемы**. Новые частные операторы или библиотека правил не добавлялись. Старый `information_action.py` и весь controller PR #140 неизменны.

`raw_entry.py --request <file> --output <json> --codex <exe> --cwd <empty-directory>` — исполняемый локальный вход. Он не установлен в обычный cloud ChatGPT и не меняет канонические runtime-файлы.

## До запуска зафиксировано

Запросы извлечены дословно из входов E2/E1 файла `tests/expert-answer-exemplar-v1.md`. Не использовался прежний вручную правильный контракт `natural-e2-fragment.json`. Полный исходный natural-office prompt по-прежнему отсутствует; этот опыт проверяет замороженный исходный **E2 Trendyol**, не выдуманную реконструкцию бюро.

Оборванное окончание E2 «дорогую автоматизацию выбирать сейчас» оставлено дословно. Его смысл не исправлялся на «рано». Контрольный ответ сам заметил обрыв. Из этого неоднозначного текста нельзя вывести точную отрицательную доступность пилота.

Одинаковые условия всех завершённых вызовов:

- Модель `gpt-5.6-sol`, effort `high`; app-server подтвердил тот же model ID.
- ChatGPT subscription auth проверен через `account/read`; API fallback отсутствует.
- Одинаковые BASE, output schema, developer instructions, read-only sandbox, cwd; fresh threads. Plugins/apps/MCP отключены, инструментальные действия актору запрещены. В сохранённых completed items только userMessage/reasoning/agentMessage.
- Context SHA-256 `d91bb2040f1a62a91b9c169639fb4618ea1e761d563a9eaa5844225165cd7f78`.
- Внутри пары E2 inputTokens одинаковы: 10,499. E1: 10,509 из-за другого текста запроса.
- Контроль тоже извлекает условия и draft с той же схемой, но host не применяет оператор. Это **instrumented baseline**, не обычный ChatGPT и не чистый тест эффекта самого извлечения.
- Максимум четыре attempted model turns. Конфигурация/критерии сохранены runner до первого запроса. После результата семантические условия/оператор/prompt не корректировались.

## Фактический расход и технический сбой

Первый baseline E2 остановился: адаптер ошибочно отклонил нормальное событие `userMessage`. Сервер был завершён. Локальный rollout содержит task_started/user message, но не token_count/завершённый ответ. Это **инфраструктурный сбой, не behavioral FAIL и не нулевой расход**. Попытка сохранена и консервативно засчитана в лимит.

Исправлена обработка события без изменения BASE/schema/model/effort. Оставшиеся три слота: candidate E2, candidate E1, baseline E2. Полная пара E1 не выполнялась. Никаких дополнительных reviewer/recovery/model calls после этих четырёх попыток.

Завершённые три turns: **34,456 total tokens = 31,507 input + 2,949 output**, включая 1,468 reasoning output; cached input 0. Расход прерванной попытки UNKNOWN и не включён в сумму. Платный API не подключался.

**Отрицательный результат — именно применимость механизма на исходном E2.** Модель не подменила отсутствие данных доказательством отсутствия доминирующего пилота. Старый оператор требует `dominant_safe_pilot=no`; корректный UNKNOWN не проходит этот gate. Значит, прежний вручную заполненный `no` скрывал существенную предпосылку. Ошибка в этой наблюдаемой цепочке находится на границе **контракт → применимость оператора**, а не в незагрузившемся исходном запросе и не в пропущенном вызове CLI.

Это не доказательство, что модель неправильно извлекла наличие пилота: UNKNOWN здесь обоснован. Также не доказано, что оператор должен в любой ситуации игнорировать UNKNOWN. Установлено более узкое: текущая конструкция не реализует обещанное восстановление кандидата на исходном входе без заранее подставленной предпосылки. Если бы сам draft снова пропустил вопрос, обязательный вызов данного оператора его здесь не восстановил бы. Это условный вывод из реально наблюдённого action=null, не искусственный модельный FAIL.

Оба E2 draft уже содержат приблизительный вопрос; различия текста не вызваны оператором, который ни один draft не изменил. Нет основания заявлять causal candidate advantage. Candidate просит дополнительные объёмы; поэтому строгий критерий «только минимальное краткое уточнение» не объявляется безусловно пройденным. E1-ответ в основном пересказывает пример и не доказывает общего экспертного ремонта.

## Оставшийся барьер

Вход теперь действительно вызывает оператор из исходного текста; прежний барьер ручного вызова в этом локальном host снят. **Полезность оператора не подтверждена:** его gate требует отрицательного знания о пилоте, которого исходный запрос не содержит. Семантическая достаточность approximation остаётся выводом модели, не независимым фактом. Точное совпадение цитат этого не сертифицирует.

Отрицательный результат сохранён без подстройки значений/оператора и без пятого вызова. Следующий дизайн должен отдельно решить эту границу применимости, а не расширять список частных операторов или выдавать UNKNOWN за no. В обычный ChatGPT этот вход не развёрнут. #136 OPEN.
