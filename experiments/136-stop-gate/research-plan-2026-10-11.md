# #136: исследование и план проверки технического решения

Дата: 2026-10-11. Статус: исследование / предложение эксперимента, не исправление. Владелец текущего статуса — Issue #136. PR #137 — отдельная непроверенная гипотеза доставки skills; PR #140 — узкий прототип проверки завершения; #26 — только откат.

## Вывод

Наиболее выгодная гипотеза: использовать доступную модель через поддерживаемый Codex runtime, вынести цель, состояние исполнения и критерии завершения в небольшой внешний контроллер, добавить независимую проверку только для сложных решений. Сначала проверить существующий runtime и готовые точки вмешательства, затем писать недостающий адаптер. Не мигрировать всю личную систему в новый framework ради эксперимента.

Ни инструкции, ни память, ни Stop hook по отдельности не покрывают #136. Внешний контроль может обнаружить отсутствующий результат и обеспечить ограниченную попытку восстановления; он не превращает плохое решение в хорошее. Для E1–E5 нужны отдельные проверки качества выбора, сохранения цели и действительного результата.

Исследование включает материалы репозитория, первичные исследования, официальную документацию и сообщения пользователей в issue trackers. Это доступная выборка, а не все существующие ресурсы. Опубликованных вероятностей исправления именно Ron OS нет.

## Что известно из проекта

Изучены #136 и обсуждение, BOOTSTRAP.md, PROTOCOL.md, эталон E1–E5, поведенческие тесты, связанный эксперимент #137 и доступные записи испытаний. Повторяющиеся сбои E1/E2/E4 при отдельных успехах E3/E5 опровергают вывод «инструкции есть, значит поведение обеспечено». Успех одной свежей сессии не доказывает устойчивость обычного интерфейса. Ранее полученные прогоны с разными средами и контекстом нельзя считать контролируемым сравнением моделей.

Наблюдаемая цепочка: не предложен дешёвый полезный способ получить информацию → выбрано слабое действие → сдвинулась цель → ответ завершён без исполнения → признание ошибки не вызвало восстановление. Внутренняя причина на уровне весов модели неизвестна. Возможные причины — генерация вариантов, их ранжирование, перегрузка контекста, недоставка нужных skills, отсутствие обязательных проверок и управляемого продолжения. Они требуют раздельных тестов, а не одной общей оценки.

Прототип PR #140 проверяет реальные локальные файлы по контракту доверенного контроллера, связанному с workspace/session/turn. 20 синтетических тестов и CI подтверждают поведение проверяющего кода. Они не подтверждают исправление поведения модели. Проверка SHA256 применима к известному точному результату; для новых решений нужен предметный проверяющий механизм. Конфигурация не установлена в текущий ChatGPT runtime. Связь turn_id при продолжении и stop_hook_active ещё нужно проверить на живом поддерживаемом host.

## Что говорят внешние данные

1. τ-bench различает успех хотя бы одной попытки и устойчивость всех повторов (pass^k), проверяет конечное состояние среды. Это подходящий принцип оценки; старые показатели моделей не являются прогнозом #136.
2. MAST анализирует сбои агентных систем по дизайну системы, взаимодействию и проверке задачи. Это аргумент исследовать контроллер и верификацию, но не диагноз конкретной модели Ron.
3. Исследование intrinsic self-correction 2023 показывает, что просьба пересмотреть ответ без внешнего сигнала может ухудшать результат. SCoRe показывает, что обучение с изменением весов может улучшить самокоррекцию. Поэтому нельзя ни обещать исправление промптом, ни утверждать, что самокоррекция принципиально невозможна.
4. Исследования reliability и scaling показывают: способность решать задачи, устойчивость и польза нескольких агентов — разные величины. Дополнительные агенты дают расход и могут распространять ошибку. Постоянный swarm не оправдан ограниченными лимитами.
5. Практика Anthropic для длительных задач использует сохранённое состояние, небольшие этапы и проверку результата: сжатия истории недостаточно. Это переносимый инженерный принцип, а не доказанный универсальный рецепт для личного ассистента.
6. Сообщения пользователей Codex и Claude Code описывают раннюю остановку, потерю цели и планы без исполнения. Это независимые сходные случаи, не статистика распространённости; закрытие issue не равно подтверждённому исправлению.

## Альтернативы и вероятности

Событие для широких оценок: за две итерации на изолированных новых задачах получить хотя бы 30% относительное снижение материальных сбоев при росте расхода не более 30%, без выхода за разрешённый scope. Порог — предлагаемое инженерное правило выбора, не научно обоснованный универсальный норматив. Все диапазоны ниже — субъективные предварительные оценки, а не измеренные частоты или доверительные интервалы. Они условны: подходящий host, те же инструменты, честные критерии и доступ к модели действительно существуют. Маленький пилот сам не сможет надёжно подтвердить такой эффект.

| Подход | Оценка шанса широкого улучшения | Зачем / ограничение |
|---|---:|---|
| Ещё инструкции без изменения исполнения | 5–20% | Дёшево, но повторяет уже слабую гипотезу |
| PR #137: доставка и активация skills | 15–35% | Проверить загрузку полезно; не обеспечивает завершение |
| Смена модели при одинаковых условиях | 25–50% | Может улучшить выбор; нужна доступность и парное сравнение |
| Краткий актуальный контекст и проверенная загрузка | 35–60% | Снижает недоставку и конкуренцию инструкций; не гарантирует верное действие |
| Только внешний Stop/результат gate | 20–40% | Широкая проблема включает семантические ошибки |
| Выборочный независимый критик | 40–65% | Может найти упущенный вариант; зависит от качества и цены |
| Минимальный контроллер + выборочная проверка + проверенная модель | 60–80% | Предпочтительная совокупная гипотеза; не сумма процентов |
| Только переход на другой framework | 10–30% | Переносит те же ошибки и добавляет интеграционные |

Для узкой задачи «есть заранее проверяемый результат, агент остановился без него» оцениваю шанс полезности внешнего gate в 75–90% при работающем продолжении. Это другое событие, его нельзя подставлять вместо вероятности исправления E1–E5. Вероятность универсального исправления обычного облачного ChatGPT из доступных настроек сейчас не определена: подтверждённой точки перехвата и принудительного продолжения нет.

## Практический план с ограничением расхода

### 1. Проверить поверхность исполнения до разработки

Проверить поддерживаемый Codex CLI/app-server host, авторизацию подпиской, один настоящий модельный ход, инструмент, Stop, продолжение и чтение результата. Список моделей и успешный процесс не доказывают доступность inference или исполнение задачи. Не переносить OAuth токены в публичный CI. В текущем Work окружении codex CLI отсутствует, локальный Stop hook нельзя зарегистрировать в облачную оркестрацию.

Сначала рассмотреть готовый OpenClaw Codex runtime: документация явно описывает relay Stop → before_agent_finalize и revise для дополнительного прохода, а также блокирование native tools. Это кандидат адаптера, не проверенная установка. Hermes документирует Codex app-server через подписку, но в этом режиме часть его внутренних memory/todo/delegation инструментов недоступна, вспомогательные задачи также расходуют подписку. Если готовый адаптер тяжелее узкой обёртки или не проходит тест — использовать минимальный контроллер поверх поддерживаемого runtime. Не запускать платный API как скрытый запасной путь.

Критерий выхода: реальный trace с правильной привязкой к задаче, ограниченным продолжением и проверенным результатом. Если host недоступен, зафиксировать точную границу и не объявлять платформу развёрнутой.

### 2. Вынести управление задачей из свободного текста

Контроллер хранит исходную цель, scope, версию релевантного контекста, активный этап, бюджет и критерии принятия. Репозиторий остаётся источником канона; контроллер хранит снимок конкретной задачи, не новый независимый канон. Агент не может сам превратить «обещал» в «выполнено».

Завершение разрешается по наблюдаемым свидетельствам: файл/тест/read-back внешней записи/предметный результат. Простое наличие tool call, exit 0, turn.completed, красивого плана или признания ошибки недостаточно. При отсутствующем результате — одна ограниченная попытка восстановления. После неё точный BLOCKED/UNVERIFIED с фактами. Повтор внешних записей требует проверки предыдущего состояния и идемпотентности.

### 3. Отдельно улучшить выбор решений

Для неоднозначной, дорогой или стратегической задачи перед исполнением вызвать независимое рассмотрение исходного запроса и доступных фактов в чистом контексте. Сначала сформировать собственное предложение, затем сравнить его с предложением исполнителя: так уменьшается привязка к первому ответу. Проверять дешёвое получение недостающей информации, цель, ожидаемый выигрыш и стоимость следующего шага. Для простой обратимой операции пропускать этот этап.

Не требовать механически три варианта в каждом ответе: такой подход уже не обеспечил нужное поведение. Проверять содержание альтернатив и реальный следующий шаг. Начальный лимит — критик максимум для 10–20% сложных задач, одна проверка, без бесконечного спора агентов. Порог уточнить по фактическому расходу.

### 4. Провести короткое парное сравнение

Заморозить шесть семейств: нахождение дешёвого решения, приоритеты, сохранение цели после отвлечения, исполнение, восстановление после критики, корректная остановка при реальном барьере. Использовать новые формулировки и безопасные sandbox-данные; жизненные домены только контрольные примеры.

Пилот: четыре парных случая = восемь запусков baseline/candidate с одинаковыми моделью, инструментами и снимком контекста; порядок чередовать. Отбросить явно бесполезную гипотезу. Для выжившего варианта — ещё 12 пар = 24 запуска с повторами и новыми задачами. Максимум 32 actor runs + 6 выборочных reviewer calls; не более одного recovery на случай. Это верхняя граница предлагаемого опыта, не уже потраченный бюджет. Если лимиты недостаточны — сократить опыт и честно оставить неопределённость.

Раздельно сохранять первоначальную ошибку, восстановление, фактический итог, цель/scope, ненужную передачу работы пользователю, расход и задержку. Оценщик видит исходную задачу и следы исполнения; семантический reviewer проверяется на заранее известном хорошем и плохом результате. Текст ответа не единственный источник оценки. Не сравнивать ordinary ChatGPT с Work как будто менялась только модель.

### 5. Принять решение по свидетельствам

Ранний критерий продолжения: заметное улучшение на held-out случаях, отсутствие запрещённых действий, ограниченный расход. При нулевом улучшении закрыть гипотезу, сохранить отрицательный trace. Если ломается инструмент/авторизация, исправлять интеграцию, не маскировать это новым промптом.

После успешного пилота — 3–5 разрешённых обычных задач с автоматической фиксацией результата. Устойчивость оценивать по повторениям и разным семействам, а не одному PASS. Даже 0 сбоев из 12 независимых одинаково распределённых испытаний допускает одностороннюю 95% верхнюю границу частоты сбоев около 22%; из 60 — около 4.9%; для около 1% нужны примерно 300. Реальные задачи неоднородны, поэтому эти числа — иллюстрация недостаточности малой выборки, не сертификат.

### 6. Разворачивать только подтверждённый вариант

Сначала ограниченный scope и наблюдаемость, затем расширение. PR #137 проверять отдельно на фактическую доставку skills. PR #140 использовать как proof of concept, заменив точные SHA256 критерии предметными проверками там, где нужен новый результат. #26 применять только при необходимом откате. Не менять всё одновременно: иначе нельзя понять, какой механизм помог.

## Что ещё не доказано

- Live Stop continuation, session/turn binding и поведение при ошибке hook на выбранном host.
- Возможность предметного oracle для E1/E2/E4, отличающего содержательное действие от имитации.
- Устойчивость после compaction и в обычной пользовательской среде.
- Результат парного сравнения при одинаковом контексте и инструментах.
- Стоимость дополнительных вызовов в фактических лимитах аккаунта.

Доступная реализация сейчас — узкий checker и его проверка. Доступное исследование выявило поддерживаемые технические пути, но не развернуло их в облачный ChatGPT. Главный барьер — отсутствие контролируемого runtime, способного перехватить завершение и продолжить эту же задачу, вместе с необходимостью надёжной семантической проверки.
